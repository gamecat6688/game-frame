# 业务协议、状态同步与存档

本实现参考 idle-rpg 的“私有存档 → 客户端状态 → 模块脏同步 → 条目通知”分层，并补齐持久化、版本恢复和幂等提交。装备替代芯片作为示例领域。

## 协议与生成

| 来源 | 用途 | 生成位置 |
|---|---|---|
| `contracts/shared/Command.proto`、`GameResponse.proto` | 业务命令和组合响应入口 | `game/internal/protocol/`、`client/protobuf/generated/api/` |
| `contracts/shared/gamestate/` | 公开状态聚合与各模块视图 | 同上；Godot 保留源协议的目录层次 |
| `contracts/shared/notification/`、`battle/` | 模块通知、战报 | 同上 |
| `contracts/server/playerstate/` | 私有 PlayerRecord 与各模块 Dbo | `game/internal/persistence/`，不生成到 Godot |
| `contracts/server/storage/` | 请求回执与存档校验信封 | 同上，仅供权威宿主使用 |
| `contracts/generated/` | excel2pb 生成的静态配置协议 | 保持原表格流水线 |

从仓库根目录运行 `./tools/generate_proto.ps1`，递归发现共享和私有目录中的 `.proto`，生成 Go、Godot 以及集成测试用的 Python 消息。先在独立临时目录完成全部生成，再同步目标并移除过时的 `.pb.go`、`.proto.gd`（及对应 UID）和 `_pb2.py`，防止重命名后重复注册旧类型。生成器失败时保留上一份产物。`tools/build.ps1` 会执行此步骤，即使设置了 `-SkipTables`。修改业务或存档 proto 后需要重建 DLL 和服务器。

目录参考 idle-rpg，按协议职责与业务模块拆分：

```text
contracts/
├─ shared/
│  ├─ Command.proto
│  ├─ GameResponse.proto
│  ├─ gamestate/
│  │  ├─ StateUpdate.proto
│  │  ├─ wallet/WalletState.proto
│  │  ├─ heroes/HeroesState.proto
│  │  ├─ equipment/EquipmentState.proto
│  │  ├─ formation/FormationState.proto
│  │  ├─ campaign/CampaignState.proto
│  │  └─ idle/IdleState.proto
│  ├─ notification/
│  │  ├─ Notification.proto
│  │  └─ equipment/EquipmentChanges.proto
│  └─ battle/Battle.proto
├─ server/
│  ├─ playerstate/
│  │  ├─ PlayerRecord.proto
│  │  ├─ wallet/WalletDbo.proto
│  │  ├─ heroes/HeroesDbo.proto
│  │  ├─ equipment/EquipmentDbo.proto
│  │  ├─ formation/FormationDbo.proto
│  │  ├─ campaign/CampaignDbo.proto
│  │  └─ idle/IdleDbo.proto
│  └─ storage/
│     ├─ RequestReceipt.proto
│     └─ SaveEnvelope.proto
└─ generated/                     excel2pb 配置协议，保留原生成流程
```

每个文件负责一个模块或聚合入口，紧密相关的小消息可以放在同一个文件，例如 `HeroesState.proto` 包含 HeroState 与 HeroesState，`Battle.proto` 包含 Fighter、BattleEvent 和 Battle。所有字段独占一行，消息之间空一行。

共享 import 以 `contracts/shared/` 为根；私有协议还可 import 共享协议，例如 RequestReceipt 引用 Command 与 GameResponse。共享协议不得反向依赖私有协议，Godot 生成命令只使用共享 include 路径。

目录拆分保留 `gameframe.protocol` / `gameframe.persistence` 的完整消息名称和 Go package，Go 业务代码不需要更换 import。Godot 从独立 Command/GameResponse 脚本加载入口，Python 按模块导入。

游戏命令与响应通过 WebSocket 长连接的二进制消息传输，一条消息对应一个 Command 或 GameResponse，不添加 JSON 或自定义长度前缀。本地 DLL 保留字符串 C ABI，生命周期控制包是 JSON；`command` 操作的 `payload` 是 Base64 编码的相同 protobuf 字节，返回包也包含 protobuf `payload`。桥接层不再接收 JSON 业务命令，业务数据不经过 JSON 数值转换。

当前请求协议版本为 2，未知字段、无效版本和非法参数会被拒绝。现阶段修改协议后统一重新生成和构建客户端、DLL、服务器，不维护旧协议兼容。共享协议的重复数值字段显式设置 `packed=false`，适配当前 GDScript 生成器；不要直接删除此设置。版本号和资源数量使用整数，Godot 测试覆盖了超过 JavaScript 安全整数范围的 `int64`。

## 命令约定

每条命令都携带 `protocol_version=2`、非空 `id`（最多 128 字节）和非负 `expected_revision`。写命令必须使用当前版本；只读命令不推进版本，也不保存幂等回执。

| `type` | 操作参数 | 行为 |
|---|---|---|
| `snapshot` | 无 | 返回六模块全量状态 |
| `state.sync` | 无 | 版本相同返回 Idle，否则返回全量 |
| `hero.level_up` | `hero_id > 0` | 升一级，由服务端计算价格、扣费和属性 |
| `equipment.equip` | `hero_id > 0`、`equipment_id >= 0` | 穿戴已拥有装备；`equipment_id=0` 表示卸下 |
| `formation.save` | `formation` | 保存恰好五名已拥有且不重复的英雄，顺序决定槽位 |
| `campaign.battle` | 无 | 挑战服务端记录的当前关卡并返回战报 |
| `idle.claim` | 无 | 按宿主时钟计算并领取收益 |

无关参数必须为默认值，例如升级不得同时携带装备 ID 或阵容。请求不接收玩家档案路径、收益、伤害、胜负或客户端计时。成功写命令都会推进版本并保存回执，包括战斗落败或保存与当前相同的阵容；业务失败不推进版本。

## 精简响应

`GameResponse` 只包含五个字段：

```proto
message GameResponse {
  string id = 2;
  string code = 4;
  StateUpdate update = 5;
  repeated Notification notifications = 6;
  Battle battle = 7;
}
```

- `id` 关联请求、过滤迟到响应并避免重复完成事件。
- `code="ok"` 是唯一成功标志，其他非空值是错误码。缺失 code 的响应无效；不能把空值当成功。
- `update` 和 `notifications` 负责同步模块状态与装备条目；`battle` 只在战斗结果中出现。
- 删除原 `ok`，避免与 code 重复表达结果；Godot 展示层需要的 `result.ok` 由 GameProtocol 解码时计算，不在 protobuf 中传输。本地桥接 JSON 外层的 ok 仍只表示桥接调用是否成功。
- 删除响应中的 `protocol_version`，版本由 `Command.protocol_version=2` 和 WebSocket 子协议 `gameframe.v2` 检查。旧版本请求在执行规则前拒绝；旧握手不能建立业务连接。
- 不需要的字段直接删除，不添加 reserved 或旧字段转换逻辑。

客户端、DLL 和服务器需要配套构建，只使用当前响应格式；protobuf 存档只接受当前 schema 3，不兼容旧回执。

## WebSocket 连接

- 默认地址 `ws://127.0.0.1:18080/ws`，子协议 `gameframe.v2`；公网部署使用 `wss://` 和有效证书。
- 握手用 `Authorization: Bearer <token>` 验证身份，当前为单开发档案的 token。账号验证允许使用 HTTP；未来接入账号服务后，用其会话凭据替换开发 token，并在连接建立时绑定对应玩家。
- 已移除 `POST /command`，不保留 HTTP 玩法回退。`GET /health` 仅用于进程健康检查。WebSocket 自身的 HTTP Upgrade 握手不承载游戏业务命令。
- 服务端使用 `coder/websocket`，同一连接串行读命令和写响应；不同连接共享 Runtime 的事务互斥。默认 Origin 验证保持开启。
- 仅接受二进制消息，文本消息关闭码为 1003，超过 64 KiB 的命令关闭码为 1009；非法 protobuf 返回 `invalid_request`，不执行规则。
- 服务端每 15 秒 ping，10 秒未得到 pong 则关闭连接；Godot 每帧 poll 处理控制帧，也每 10 秒发送 ping。传输心跳不修改玩家版本，和 `state.sync` 分开。
- 客户端连接/响应超时为 5 秒，断线后按 1、2、4、8 秒间隔重连，上限 8 秒；成功建立连接后重置退避。重连前保留同一条待确认命令的原始 protobuf，连接恢复后重发，避免更换 ID 导致重复扣费。
- 单条命令累计 3 次连接/响应失败后清除待确认载荷，报告网络错误并解除 busy，后台仍继续重连；后续恢复通过 `state.sync` 对齐服务器真实状态。不能将网络错误解释为服务器未执行。选中的子协议不匹配、收到文本响应或超过 1 MiB 的响应时属于终止性错误，客户端关闭连接并停止此次会话的自动重连。
- 空闲断线也会自动重连；恢复连接后，若有待确认命令先完成重发，再执行 `state.sync`，必要时全量恢复。没有初始快照时重新请求 `snapshot`。
- 响应按请求 ID 关联；迟到的其他请求响应不会确认当前命令。切换模式和退出会关闭连接，清空待发送数据并取消重连。

当前原生客户端使用 Godot `WebSocketPeer.handshake_headers`。浏览器导出不支持自定义握手头，后续如支持 Web 导出，需要独立实现同站会话 Cookie 或短期票据认证。当前也未加入主动业务推送；模块增量和通知随 WebSocket 命令响应返回。

## 状态和通知

业务核心保留内部领域状态，但只通过显式转换输出以下公开模块：

- Wallet：金币、经验。
- Heroes：英雄等级、穿戴和服务器计算后的属性。
- Equipment：拥有的装备及其使用者。
- Formation：上阵槽位。
- Campaign：当前关卡。
- Idle：当前可领取收益；私有结算时刻不下发。

每次构建 StateUpdate 都包含 `revision/config_version/server_time` 和最新 Idle 视图；Idle 是派生值，不要求推进存档版本。下表列出在此基础上的业务模块与通知：

| 操作 | 额外同步内容 |
|---|---|
| 升级英雄 | Wallet、Heroes |
| 穿戴/卸下 | Heroes、装备所有者的绝对值 upsert 通知 |
| 保存阵容 | Formation |
| 领取挂机收益 | Wallet；同时更新私有领取时刻并标记 Idle |
| 战斗胜利 | Wallet、Campaign、战报 |
| 战斗失败 | 战报；持久化版本仍递增以保存回执 |

穿戴或卸下会标记 Heroes 和 Equipment；只有装备所有者实际变化时才发送 upsert 通知。业务错误由 Runtime 返回当前六模块全量状态；解码失败等传输前置错误则可能仅有 `code`。

模块未出现在增量中表示“不变”；模块出现时整体替换，因此 0、空列表都能正确生效。不能直接使用 protobuf `MergeFrom` 代替这些语义。

EquipmentChanges 支持 `upsert` 和 `deleted_ids`，客户端按 ID 合并，使用绝对值而不是“增加 N”。当前穿戴/卸下业务实际发送 upsert；删除机制有 Go/Godot 测试覆盖，原型尚未添加出售/分解按钮。新增此类业务时，从候选状态移除装备并标记 Equipment，若它已穿戴还必须更新 Heroes。

`dirtyModules` 随命令事务创建，规则成功修改数据后调用 `MakeDirty`；响应构建不清理脏标记。落盘成功后才替换内存并清理。`dirtyCovers` 检查实际变化是否覆盖了必需模块，防止新增规则忘记标脏而产生客户端陈旧状态。

## 版本、重试与全量恢复

StateUpdate 只带三个同步元数据：`revision`、`config_version` 和 `server_time`，其余为六个业务模块。全量与增量通过模块是否齐全判断，不再传递 `full` 和 `base_revision`。

1. 首次进入、主动 `snapshot` 请求或状态过期时，返回全部六个模块；即使模块内容为空，也必须保留该 message 的存在标记。
2. 正常写入将版本从 N 推进到 N+1，并返回增量；不支持跨多个版本聚合增量。
3. 每 5 秒的 `state.sync` 在版本相同时只带当前 Idle 视图，版本保持不变；版本不一致则返回全量。
4. 客户端没有基线或收到跳过版本的增量时保留原状态，自动请求 `snapshot`，完整恢复后再报告原操作结果。
5. 已应用的增量、较旧版本、同版本但更旧的时间视图会被忽略。同版本的非全量响应只允许刷新 Idle，且不得包含通知；其他同版本增量视为已应用的回执。失败命令不推进版本。

`PlayerStateStore` 在临时候选数据上验证并合并完整响应，最后一次性提交；冲突通知不会造成钱包已改、装备没改的半更新。它发布受影响的模块列表，GameSession 对外转发 `state_changed(modules)`。现有原型的单个 Presenter 仍统一刷新展示值；将来拆成多个 Presenter 时可以按模块订阅。

请求 ID 与完整命令一起用于幂等校验。最近 64 条成功回执随状态保存，DLL/服务器重启后仍能返回原结果；相同 ID 不同参数被拒绝。回执淘汰后旧命令也会因 `expected_revision` 过期而被拒绝。客户端重试复用请求 ID，重复响应不会重复发布完成事件。

## SaveToDB 与文件存储

`Runtime.SaveToDB()` 保存当前已提交状态；正常写命令使用它所共用的 `saveRecord(candidate)`，在发布内存状态前持久化候选事务。

存档使用 PlayerRecord schema 3，保存私有模块 Dbo 和按顺序排列的请求回执。英雄战斗属性等可派生数据不存入 Dbo；挂机的 `last_claim_at` 只保存在私有协议中。外层 SaveEnvelope 使用 `magic="EMBER_PLAYER"`、`format_version=1`，包含 PlayerRecord 字节和 SHA-256，用于检测损坏，不用来防止玩家主动修改单机文件。读取上限为 16 MiB。这里的存档 schema 3、信封格式 1、请求协议 2，以及 `Rules.Version` 配置版本是不同概念；内部领域状态的 `Schema=1` 不代表 protobuf 存档仍使用旧 schema。

当前文件 Store 的提交步骤：

```text
候选状态 + 新回执
    → protobuf PlayerRecord
    → 带 SHA-256 的 SaveEnvelope
    → 目标目录中的临时文件
    → Write / Sync / Close
    → 替换目标文件：Windows MoveFileExW / 非 Windows os.Rename
    → 发布内存状态与响应
```

序列化或写入失败时返回 `save_failed`，保持原内存状态，清理临时文件；重试同一命令仍可正常执行。只有保存成功才记录新回执，避免“请求被去重但状态未落盘”。重命名失败不会覆盖原目标。已测试连续替换、失败后目标保留、无临时文件残留，以及重新打开存档后的完整状态和回执。

Windows 分支使用 `REPLACE_EXISTING | WRITE_THROUGH`；Linux Docker 服务器使用非 Windows 分支的 `os.Rename`。两个分支都会先同步临时文件，但当前未对父目录执行同步，不能据此承诺断电后目录项一定持久化。

这仍是单写入者的文件后端：一个存档应由一个 Runtime/服务器进程拥有。进程内互斥锁不能解决多个服务器进程同时写同一路径的问题。正式多实例存储应实现数据库版本条件更新和事务，把玩家状态与幂等回执一起提交。当前没有声称完成多实例数据库后端或断电故障注入测试。

## 旧存档迁移

默认单机存档为 `user://offline.pb`，开发服务器为 `runtime/server.pb`；Docker 使用命名卷内的 `/data/server.pb`。服务器可用 `-save` 指定路径；路径以 `.pb` 结尾时会设置同名 `.json` 为旧档候选。

这里只保留原有 JSON 文件迁移功能；不提供旧 protobuf 存档或旧响应的兼容迁移。

- `.pb` 不存在时，文件 Store 才尝试同名 `.json`。
- 加载 v1 JSON 后验证玩家状态、配置版本和回执，将其转换为 schema 3 protobuf。
- 旧回执中的完整 Snapshot 转成完整 StateUpdate，保留命令 ID、参数、原版本和结果，避免迁移后重复扣费。
- 成功后写入 `.pb`，原 `.json` 原样保留。迁移写入失败则启动失败；下次仍可从旧文件重试。
- 已有 `.pb` 损坏、校验不符或版本不兼容时直接报错，不回退旧档、不静默创建新角色。

自动迁移只读取宿主自己的存档路径；服务器接口没有导入客户端存档的操作。单机和服务器始终使用独立存档。

## 验证

```powershell
./tools/build.ps1 -SkipTables -Test
```

包括 Go 规则和持久化测试、真实 DLL/WebSocket protobuf 一致性、长连接复用、握手认证/子协议/Origin、文本/超大消息拒绝、ping/pong 及无响应连接关闭、私有存档解码、进程重启与幂等恢复、旧 JSON 迁移、Godot 状态合并测试，以及带三语切换的静态界面 smoke。Godot 测试还会丢弃已保存命令的响应并断开连接，验证自动重连后只升级一次、只发布一次完成事件，以及空闲断线自动恢复。测试使用临时端口和独立存档，不改玩家默认进度。

精简响应的验证还覆盖：从 code 判断成功或失败，以及缺失 code 的客户端拒绝行为。

`-Test -Headless` 仍运行状态和界面交互断言，但不输出截图；静态场景、语言、桥接或协议修改应使用有显示的 smoke 并检查截图。Docker 镜像与卷恢复通过独立的 `tools/test_docker.py` 验证，准备步骤见 [Docker 部署](Docker部署.md)。
